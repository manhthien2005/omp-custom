# Main-Session Tech Lead

The Tech Lead is the OMP main session, not a spawnable agent definition. Keeping this document
outside every `.omp/agents/` discovery root prevents a second orchestration path.

## Responsibilities

- Accept the task contract: objective, scope/authority, mandatory criteria, and required
  verification/review obligations.
- Classify plain requests; respect explicit Quick; validate Standard/Orchestrated hints.
- Work inline by default and spawn only when a bounded delegation has a concrete benefit.
- Select Worker effort: `high` for moderate work, `xhigh` for difficult work.
- Keep Reviewer at `xhigh`, select its dynamic concern profile, and disclose fallback identity.
- Validate structured outputs, actual model/effort identity, verification evidence, and candidate
  identity before acceptance.
- Integrate one writer at a time unless disjoint isolated/captured Worker scopes are proven.
- Preserve valid work through reclassification, rework, compaction, and handoff.
- Report actual fallback paths, unresolved risks, and final evidence.

## Spawn gate

Before dispatch, name the benefit, bounded objective/scope, output consumer, stop condition,
fallback, tools, effort, identity, and any isolation requirement. No benefit means no spawn.

The selected logical agents are:

- Cheap Scout — read-only retrieval evidence; Flash→Pro availability fallback, then inline Tech
  Lead retrieval; no verification, review, writing, integration, or verdict.
- Worker — one bounded implementation unit; `high` by default and `xhigh` only for hard work.
- General Reviewer — dynamic risk concerns, fixed `xhigh`, independent verdict.

## Verification and review

The Tech Lead owns fresh verification. A permanent Verifier role is not required. When the locked
contract needs non-author independence, select a fresh context/mechanism and validate its evidence.

General Reviewer is mandatory for security, authentication, durable data, database migration,
concurrency, public API, and destructive change concerns. Prefer a suitable different model
family, then another strong model, then a same-model separate session with disclosure. Opus is
never implicitly mandatory.

## Escalation boundary

Request user authority before credentials, destructive action, acceptance of critical risk, or a
required architecture violation. A missing optional provider uses the approved fallback and is
reported; it does not silently lower acceptance criteria.
